# ロータリーエンコーダスクロール調整の学び

## 概要

ZMKファームウェアでロータリーエンコーダのスクロール挙動を最適化するプロジェクト。当初の「少ない回転で反応しない」「大きく回すとスクロールしすぎ」という問題を、パラメータの正しい理解と調整で解決した記録。

## ハードウェア仕様

- **エンコーダ**: EC11
- **steps**: 80 (1回転あたりのパルス数)
- **デテント数**: 24 (1回転あたりのクリック数)
- **動作環境**: macOS

## 主要パラメータの理解

### 1. `triggers-per-rotation`

**誤解していたこと:**
- 小さくすれば敏感になると思っていた（8, 10など）
- 整数比でないと動作しないと思っていた
- **デテント数（24）に合わせるのが正解だと思っていた**（Phase 5 で覆る）

**正しい理解:**
- ZMK sensor は `steps ÷ triggers-per-rotation` の pulses を累積して 1 発火する
- **整数比にできれば整数比を優先する**（非整数比は初動空振りを起こす、Phase 5 参照）
- 80 steps 環境なら 20 / 40 / 80 が整数約数
- デテント数と一致させる（24）は「概念的に分かりやすい」だけで、実運用では劣る

**設定値の変遷:**
- 元: 30
- Phase 3 での結論: **24** （デテント数に合わせた）→ 初動空振りが残る
- **最終: 40** （steps の 1/2、2 pulses/trigger、Phase 5 参照）

### 2. `tap-ms`

**誤解していたこと:**
- ステップ累積のウィンドウ時間だと思っていた
- 短くすれば反応が良くなると思っていた（10msなど）

**正しい理解:**
- **`&msc`を押している時間**を指定
- `&msc`の内部イベント周期は**16ms**
- `tap-ms < 16ms` だと **1回もイベントが出ずゼロ**になる
- 長すぎると1回の発火で複数イベントが出て「バースト的にスクロール」

**設定値:**
- 元: 20ms
- 試行: 100ms → ゆっくり回すと一気にスクロール（NG）
- 試行: 10ms → 一切反応しない（NG、16ms未満のため）
- 最終: **20ms** （イベント発火に必要な最小値）

### 3. `ZMK_POINTING_DEFAULT_SCRL_VAL`

**誤解していたこと:**
- これで反応性も変わると思っていた

**正しい理解:**
- **スクロール量（速度）のみ**を調整
- 反応性は`triggers-per-rotation`で決まる
- macOSが認識できる最小値がある（60だと小さすぎて無反応だった）

**設定値:**
- 元: 230
- 試行: 60 → 反応しない（macOSが認識できないレベル）
- Phase 3 での結論: **120** （元の約半分の速度、適度なバランス）
- Phase 5 での経過: 120 → 140 → 170 → **120**（triggers-per-rotation=40 と組み合わせて元値に戻る）

## パラメータの関係性

```
反応性（いつスクロールするか）
  ↓
triggers-per-rotation で制御
  ↓
デテント数に合わせる = 1デテント1発火

スクロール量（どれだけスクロールするか）
  ↓
SCRL_VAL で制御
  ↓
macOSで認識できる範囲で調整（60-230）

バースト防止（一気にスクロールしない）
  ↓
tap-ms で制御
  ↓
&mscの内部周期（16ms）以上にする
```

## macOS環境の特殊性

1. **スクロール加速**
   - macOS側にスクロール加速機能がある
   - 連続イベントは大きく感じやすい
   - Windows/Linuxとは挙動が異なる可能性

2. **最小認識値**
   - SCRL_VAL=60 だと認識しないレベル
   - 120以上が安全圏

3. **推奨アプローチ（未実装）**
   - スムーズスクロール + MOVE_Y() の組み合わせ
   - macOSとの相性が良いとのこと

## 試行錯誤の過程

### Phase 1: 感度向上の誤ったアプローチ
- triggers-per-rotation を 30 → 20 → 16 → 10 → 8 と下げた
- 結果: ゆっくり回転時の反応が悪化
- 理由: 1回の発火に必要なステップ数が増えすぎた

### Phase 2: tap-ms調整の失敗
- tap-ms を 100ms に上げた
- 結果: ゆっくり回転時に一気にスクロール
- 理由: 累積時間が長すぎて複数イベントがバースト

### Phase 3: Codex相談による突破口
- デテント数（24）の情報を提供
- Codexが正しいパラメータの関係性を教えてくれた
- triggers-per-rotation=24 が正解だと判明

### Phase 4: tap-ms=10の落とし穴
- Codexの推奨でtap-ms=10にした
- 結果: 一切反応しない
- 原因: &mscの内部周期（16ms）未満だった
- 修正: tap-ms=20 に戻して解決

### Phase 5: 初動空振り問題と整数比の再発見

Phase 3 の結論（`triggers-per-rotation = 24`）で長らく運用していたが、実使用では **休止状態からの最初の 1 デテントで空振りする** 体感が残っていた。

**根本原因の分析:**
- `steps=80` / `triggers-per-rotation=24` は非整数比（80÷24 ≈ 3.33 pulses/trigger）
- ZMK のアキュムレータは休止で 0 リセット
- EC11 の 1 デテントは物理的に 3〜4 pulses ぶれる
- 最初のデテントが 3 pulses しか出ないと 3.33 の閾値未満 → 空振り
- さらに EC11 の休止位置は quadrature 中間にあり、最初の半デテントは pulse としてカウントされない

**実験と結論:**
- 試行 A: `triggers-per-rotation = 20`（4 pulses/trigger、整数比）+ `SCRL_VAL = 170` → 初動空振り改善するが「重い」体感が残る（1 デテント 3.33 pulses が 4 pulses 閾値に届かないケースが残存）
- 試行 B: **`triggers-per-rotation = 40`（2 pulses/trigger、整数比）+ `SCRL_VAL = 120`** → 初動が半デテントで即発火。体感明確に改善
- 1 デテントで 1.67 発火する副作用があるが、`SCRL_VAL` を 120 に抑えることでオーバースクロールを回避
- 1 回転あたりの total スクロール量 = 40 × 120 = 4800 で、Phase 3 の 24×120=2880 より約 67% 増（速度感も向上）

**教訓:**
- 「デテント数に合わせる」というルールは**初動空振り問題を無視した簡略化**であり、実運用では劣る
- 整数比を優先する方が「休止からの反応の一貫性」で明確に上回る
- `SCRL_VAL` は "速度" だけでなく "1 発火あたりの重み" として考え、`triggers-per-rotation` とセットで total スクロール量を設計する

## 最終設定

```dts
// boards/shields/dax5/dax5.dtsi
sensors: sensors {
  compatible = "zmk,keymap-sensors";
  sensors = <&left_encoder &right_encoder>;
  triggers-per-rotation = <40>;  // stepsの整数約数(80÷40=2 pulses/trigger)
};
```

```c
// config/dax5.keymap
#define ZMK_POINTING_DEFAULT_SCRL_VAL 120  // triggers=40 と組み合わせて total 4800/回転

enc_scroll: encoder_scroll {
  compatible = "zmk,behavior-sensor-rotate-var";
  #sensor-binding-cells = <2>;
  bindings = <&msc>, <&msc>;
  tap-ms = <20>;  // &mscの内部周期以上
};
```

## 達成した改善

| 項目 | 改善前 | Phase 3 (triggers=24) | Phase 5 最終 (triggers=40) |
|-----|--------|--------|--------|
| 少ない回転 | ほぼ反応しない | 1〜2 デテントで反応 | 1デテントで確実に即反応 |
| 休止からの初動 | 空振り連発 | **たまに空振り** | 空振りなし |
| ゆっくり回転 | 反応が鈍い | 滑らかに反応 | 滑らかに反応 |
| 速い回転 | スクロールしすぎ | 適度な速度 | 適度な速度 |
| バースト | 一気にスクロール | なし | なし |

## 今後の調整指針

### スクロール速度の微調整（triggers-per-rotation=40 前提）
- **もう少し速く**: SCRL_VAL を 140-160 に
- **もう少し遅く**: SCRL_VAL を 100 に
- **1 デテントごとのオーバースクロールが気になる**: SCRL_VAL を 100 に下げるか `triggers-per-rotation` を 20 に下げて 1 デテント 1 発火に戻す（初動空振り問題は再発する点に注意）

### `triggers-per-rotation` を変えたい場合
`steps` の整数約数を選ぶこと。80 なら選択肢は `20 / 40 / 80`:
- `20`: 4 pulses/trigger、1 発火が重め、1 回転 20 発火
- `40`: 2 pulses/trigger、**推奨**、1 回転 40 発火
- `80`: 1 pulse/trigger、極端に軽い（1 デテントで 3〜4 発火）、bounce に弱く暴走リスク

### さらなる最適化（オプション）
スムーズスクロールを有効化する場合:

1. `boards/shields/dax5/dax5_L.conf` と `dax5_R.conf` に追加:
```conf
CONFIG_ZMK_POINTING_SMOOTH_SCROLLING=y
```

2. `SCRL_*` の代わりに `MOVE_Y()` を使用:
```dts
sensor-bindings = <&enc_scroll MOVE_Y(30) MOVE_Y(-30) ...>;
```

※ macOS環境ではこのアプローチが特に相性が良いとのこと

## 重要な教訓

1. **パラメータの意味を正しく理解する**
   - 推測ではなく、仕様を確認する
   - Codexのような専門知識の活用が有効

2. **ハードウェア仕様を把握する**
   - デテント数は重要な情報
   - データシートの確認が必須

3. **環境依存性を考慮する**
   - macOS特有の挙動がある
   - クロスプラットフォームでは動作が異なる可能性

4. **段階的な調整とフィードバック**
   - 一度に複数のパラメータを変えない
   - 変更→ビルド→書き込み→テストのサイクル

5. **専門家に相談する**
   - 詰まったらCodexに相談
   - 正しい方向性を早期に得られる

## 参考情報

- ZMK Documentation: https://zmk.dev/
- EC11 Encoder Specification: 24 detents, 80 steps
- Codex診断による重要な発見:
  - `tap-ms` は押している時間
  - `&msc` の内部周期は16ms
  - `triggers-per-rotation` はデテント数に合わせるのが基本（Phase 5 で「整数比を優先すべし」と改訂）
- Phase 5 実測での発見:
  - 非整数比 `steps / triggers-per-rotation` は休止からの初動空振りを生む
  - EC11 の 1 デテント = 3〜4 pulses の物理的ぶれを吸収するには整数比が必須
  - `steps` の整数約数から `triggers-per-rotation` を選ぶ方が「デテント数一致」より体感が良い
